# PWM-LDCT v0.5 — GPU baseline run plan

Operational plan for producing the manuscript's Technical-Validation baseline numbers
(`tab:baselines_v05`) by running the **already-built** harness ([`README.md`](README.md);
`pwm_ldct_baselines`, RED-CNN + pluggable models) on a GPU. **[CONFIRM]** marks decisions.

> **Role (not a ranking).** Per the Data-Descriptor scope, this is *evidence the unified loader
> drives heterogeneous published methods to convergence and that the numbers reproduce bit-identically
> from the released container* — not a method comparison. Keep that framing.

---

## 2. Prerequisites (data quality)
- **Dataset tree**: `gs://low-dose-ct/pwm_ldct_v0_5` (v0.5 = **LIDC-only**, 1{,}010 patients,
  simulated low-dose; no AAPM/Mayo tree in v0.5). AAPM 2016 + Mayo LDCT-PD harmonized builds are
  **v1.0 roadmap** (§4) and are not needed for the v0.5 table.
- **Low-dose input quality — important:** the v0.5 simulated low-dose pairs are generated by the
  LIDC simulation pipeline (`projection_domain_v1_gpu`, dose ratios 0.10/0.25/0.50). If the
  deposited simulated low-dose was generated by the **old uncalibrated** sim (non-physical),
  regenerate it with the **calibrated** model (`I0_REF=1e8`, §4 deferred item) on GPU before
  training; do **not** substitute real reference-LD pairs, which exist only for AAPM/Mayo and are
  **v1.0 roadmap** (real reference-LD subset with `--sources mayo` / `prefer_real_ld=True`). State
  which calibration was used in the manuscript.

## 3. Compute
- **GPU**: 1× modern data-center GPU (A100/H100/V100, ≥16 GB) suffices; diffusion benefits from more.
  CT slices are 512×512 → batch size 1–4 typical. **[CONFIRM]** provider/instance.
- **Rough GPU-hours to convergence** (single GPU): RED-CNN ~4–8 · transformer ~12–24 · unrolled
  ~8–16 · diffusion ~24–72 (training + iterative sampling at eval). **Total ≈ 50–120 GPU-h**
  (~$50–360 at typical cloud rates). Diffusion eval is the slow tail (per-image sampling).

## 4. Protocol
Build once, then train + eval each model (deterministic, seed 42):
```bash
cd WS-1_dataset && docker build -t pwm-ldct-baselines:v0.5 -f baselines/Dockerfile.baseline .
# per model: train on the train split, eval on test -> results.json (per dose level)
docker run --gpus all -v /data/pwm_ldct_v0_5:/data -v $(pwd)/out:/out pwm-ldct-baselines:v0.5 \
    train --dataset /data --out /out/<model>.pt --model <model> --epochs <N> --seed 42
docker run --gpus all -v /data/pwm_ldct_v0_5:/data -v $(pwd)/out:/out pwm-ldct-baselines:v0.5 \
    eval  --dataset /data --checkpoint /out/<model>.pt --split test --out /out/<model>_results.json --seed 42
```
- **Hyperparameters**: RED-CNN Adam lr 1e-4; others per their papers (**[CONFIRM]**). Inputs are
  HU→[0,1] normalized (loader); metrics computed in [0,1] (`data_range=1`); install the `lpips`
  extra for LPIPS, else it reports `null`.
- **Per-dose eval**: `eval` already reports `sim_r010/r025/r050` and `real` separately.
- **Optional 5-tuple credentials** (`tab:credentials_v05`) are produced by the companion WS-2
  framework (severable; out of the harness's core path).

## 8. Fixed seed set (§7.3) — evaluation reporting rule

**All reported evaluations must run over the fixed seed set and report the mean AND the interval
(min/max) across seeds.** A single-seed number is never the reported evaluation.

- **Fixed seed set**: `FIXED_SEED_SET = (42, 2023, 7, 12345, 999)` in `src/pwm_ldct_baselines/eval.py`
  (this supersedes the "deterministic, seed 42" convention in §4/§6 above; seed 42 remains the
  first seed for bit-identical reproduction of previously committed results).
- **CLI**: `eval --seeds 42,2023,7,12345,999 --out <model>_results_seedset.json` runs the full set
  and writes a JSON with per-seed results plus an `aggregate` section (mean/min/max per dose level
  per metric: psnr, ssim, lpips, cnr_mean, cho_auc_mean).
- **Manuscript rule**: any PSNR/CNR/AUC transcribed into `tab:baselines_v05` / `tab:detectability_v05`
  must be the mean over the fixed seed set with the interval reported in the caption or a companion
  table; single-seed values are only allowed as "first seed" reproduction anchors.
- **Dose curve rule**: the dose–detectability curve (Rung 4) must be built from seed-set means,
  not from a single-seed run.

## 9. Container reproduction gate (§7.1)

Standing rule for every downstream comparison (WS-3 reference method, WS-4 leaderboard, any
external benchmark): **numbers reported for the WS-1 baselines must be reproduced inside the
released container** (`pwm-ldct-baselines:v0.5`, content-addressed, `Dockerfile.baseline`) —
**paper numbers from the original publications must not be quoted** as the baseline evidence.
The Data-Descriptor itself does not rank methods; the gate exists so that every comparison rests
on the same bits, the same task specification (see `task_spec.json` / `../schema/detectability_task_spec.md`)
and the same evaluation protocol (§4 double-metric pairing).

## 10. Standing measurements (Rung 2 / Rung 4 / Rung 6) — CLI entry points

Three companion tools ship with the harness as **standing measurements**; they are deliberately
standalone (independent of the GPU training path) so they can be run on any workstation:

| Rung | Tool | Entry point | Output |
|---|---|---|---|
| Rung 4 | Dose–detectability curve | `python -m pwm_ldct_baselines dose-curve` | `output/dose_detectability_curve.png` + `output/dose_detectability_stats.json` (knee = Rose-3.0 crossing by linear interpolation; `not_reached` if no crossing) |
| Rung 2 | DICOM geometric pairing check (v1.0 real-pair data prep) | `python -m pwm_ldct_baselines dicom-pairing --series <dir> [--pair-with <dir>]` | per-series geometry report + paired-slices list; pairs by `ImagePositionPatient` (never by filename order); target Pearson correlation > 0.99 |
| Rung 6 | Leave-one-vendor-out double-metric spread (GE/Siemens/Philips/Toshiba) | `python -m pwm_ldct_baselines vendor-loocv --results-glob "baselines/results/*_results_det.json"` (or `--demo` for a synthetic run) | per-fold fidelity+detectability stats + cross-vendor spread (std/min/max) JSON; standing report, not a one-off |

The vendor folds follow the standing rule that both fidelity **and** detectability must be reported
together (§4); a vendor LOOCV run that reports only one metric is not published.
